# F01 | SQL-style authentication bypass

| Field | Value |
| --- | --- |
| Risk | High |
| Status | Open - retest pending |
| Milestone | M1 |
| Affected asset | [patient login endpoint] |
| Evidence references | E15, E16; see [evidence register](../evidence/EVIDENCE_INDEX.md) |

## Observation and proof

The Burp Intruder evidence records a POST to [patient login endpoint] with a crafted username (value withheld). The selected response is HTTP/2 302 Found with Location: [patient portal]. The later browser screenshot displays a report portal containing three pathology reports with Download buttons.

## Interpretation

The behaviour is consistent with SQL injection in authentication processing: a crafted username is accepted without a valid account password being demonstrated. Source code and raw transaction exports are not available, so the precise SQL implementation remains unverified.

## Demonstrated impact

An unauthorised user could gain portal access and retrieve patient documents. Three report files are present in the submitted evidence. Broader account access, write access and arbitrary database extraction through this endpoint are not demonstrated.

## Remediation

Use parameterised queries for account lookup; verify passwords separately with a secure password verifier. Remove query construction using input concatenation. Regenerate session identifiers after login, enforce report ownership on every download, and log authentication anomalies.

## Retest acceptance criteria

Repeat the documented input and negative login tests: invalid credentials must fail without an authenticated session. Verify access with two test accounts and confirm one patient cannot download another patient's report.
